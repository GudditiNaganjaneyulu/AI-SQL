# The Relational Model and Keys

> **Why this matters:** the exam objective *"Design and implement database constraints, including PRIMARY KEY, FOREIGN KEY, UNIQUE, CHECK, and DEFAULT"* assumes you understand why keys and relationships exist.

## Keys

### Primary key (PK)

A **primary key** uniquely identifies each row. It can never be `NULL` and never repeat.

- `CustomerID` in `Customers` is a primary key.
- A **natural key** comes from real life (e.g., an ISBN). A **surrogate key** is generated by the database (e.g., `IDENTITY` or a `SEQUENCE`). Surrogate integer keys are the most common choice.

### Foreign key (FK)

A **foreign key** is a column that points to the primary key of another table. It enforces **referential integrity**: you cannot create an order for a customer who doesn't exist.

```
Customers (CustomerID PK) 1 ──────< many  Orders (OrderID PK, CustomerID FK)
```

### Other constraints you will meet

| Constraint | Rule it enforces | Example |
|---|---|---|
| `UNIQUE` | No duplicate values (one NULL allowed) | Each email appears once |
| `CHECK` | Values must satisfy a condition | `Price >= 0` |
| `DEFAULT` | Value used when none is supplied | `OrderDate DEFAULT SYSDATETIME()` |
| `NOT NULL` | A value is required | Every product needs a name |

## Relationships

| Type | Meaning | How to build it |
|---|---|---|
| **One-to-many** | One customer, many orders | FK in the "many" table (`Orders.CustomerID`) |
| **One-to-one** | One employee, one badge | FK that is also `UNIQUE` |
| **Many-to-many** | Orders contain many products; products appear in many orders | A **junction table** `OrderLines(OrderID FK, ProductID FK, Quantity)` |

## Normalization (why we split tables)

Imagine one big table:

| OrderID | CustomerName | CustomerEmail | Product | Price |
|---|---|---|---|---|
| 10 | Asha | asha@example.com | Tent | 199 |
| 11 | Asha | asha@example.com | Stove | 49 |

Problems:

- **Update anomaly:** Asha changes email → you must update many rows, and you might miss one.
- **Insert anomaly:** you can't record a new customer until they order something.
- **Delete anomaly:** delete Asha's only order and you lose Asha entirely.

**Normalization** removes these problems by giving each fact one home:

- **1NF:** each cell holds one value; no repeating groups.
- **2NF:** every non-key column depends on the *whole* key.
- **3NF:** non-key columns depend *only* on the key, not on other non-key columns.

Result: `Customers`, `Products`, `Orders`, `OrderLines` — joined back together with **JOINs** when you query.

> **Exam tip:** heavy analytics tables are sometimes deliberately **denormalized** (fewer joins, faster reads) — often with **columnstore indexes**. Know that normalization is a trade-off, not a law.

## Where JSON fits

Normalization suits data with a fixed shape. When attributes vary a lot (a tent has `capacity`, a stove has `fuelType`), storing them in a **JSON column** avoids dozens of mostly-empty columns. You'll learn this in *Domain 1 → JSON in the Database*.

## Try it

Design tables for a library: books, members, and loans (a member borrows many books over time; a book is borrowed by many members over time). Identify PKs, FKs and at least one CHECK constraint.

<details>
<summary>One possible answer</summary>

- `Books(BookID PK, ISBN UNIQUE, Title NOT NULL)`
- `Members(MemberID PK, Email UNIQUE)`
- `Loans(LoanID PK, BookID FK → Books, MemberID FK → Members, LoanDate NOT NULL DEFAULT today, DueDate, ReturnDate NULL, CHECK (DueDate > LoanDate))`

`Loans` is the junction table for the many-to-many relationship.
</details>

## Knowledge check

1. Can a primary key column contain NULL?
2. How do you implement a many-to-many relationship?
3. Which anomaly occurs when deleting a row accidentally removes other facts?

<details>
<summary>Answers</summary>

1. No.
2. With a junction table containing foreign keys to both tables.
3. A delete anomaly.
